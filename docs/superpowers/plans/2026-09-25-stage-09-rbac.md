# Stage 09 RBAC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add durable users, a bootstrap-only sole Owner, reusable server-side RBAC, and the role-aware Users dashboard.

**Architecture:** Google OIDC remains identity proof and the environment policy remains admission control. A durable MySQL user record is resolved for each session request, and shared dependencies authorize role capabilities before mutation services run. The dashboard renders only server-authorized controls but never relies on hiding them.

**Tech Stack:** FastAPI, SQLAlchemy 2, Alembic/MySQL 8, Jinja2, vanilla JavaScript, pytest.

**Spec:** `docs/superpowers/specs/2026-09-25-stage-09-rbac-design.md`

## Global Constraints

- Retain Google OIDC, opaque cookies, same-origin mutation checks, and allowlist admission policy.
- Store role/user data durably in MySQL via an additive Alembic migration.
- Never accept role data from a browser session or request body as an authorization source.
- Support exactly one Owner; no browser/API owner grant or ownership transfer.
- Do not create a git commit or begin Stage 10.

## Review Focus

- Existing opaque sessions must lose access when their durable user is disabled or removed.
- A manually recreated browser control must still receive a 403 from protected APIs.
- Case/whitespace email variants must map to one durable account and one bootstrap Owner.
- An Admin must not create, promote, disable, or otherwise alter the Owner.
- A user account must remain unusable until both the application account and Google admission policy allow it.
