# Security Design

Status: approved V1 security architecture baseline.

This document defines the security model for the standalone SkyBeat monitoring and alerting system.

V1 is designed for approximately:

```text
0–100 monitored devices
```

with:

* Linux monitoring agents
* FastAPI server
* MySQL 8.x / InnoDB
* background monitoring/notification worker
* Google-authenticated dashboard
* HTTPS
* email/SMS notifications
* single central Ubuntu VM deployment

Security controls must remain practical enough to deploy and operate within the V1 timeline.

---

# 1. Security Principles

V1 follows these principles:

```text
Authenticate every device

Authorize every dashboard user

Encrypt public traffic

Minimize privileges

Never trust telemetry

Keep secrets outside Git

Bound every external operation

Fail closed where identity is uncertain

Separate monitoring from remote control

Record security-relevant administrative actions
```

Most importantly:

```text
SkyBeat observes devices.

SkyBeat does not control devices.
```

V1 contains no:

* remote shell
* arbitrary command execution
* device reboot
* driver restart
* service restart
* package installation
* OS modification
* repair workflow
* self-healing

---

# 2. Trust Boundaries

Major boundaries:

```text
Internet / Network
       │
       ▼
Reverse Proxy
       │
       ▼
FastAPI
       │
       ├──────── Dashboard Browser
       │
       ├──────── Monitoring Agent
       │
       ▼
MySQL
       │
       ▼
Worker
       │
       ├──────── SMTP
       └──────── SMS Provider
```

Each boundary must authenticate, validate, or constrain incoming data appropriately.

---

# 3. Threat Model

Primary V1 threats include:

* stolen device credential
* fabricated telemetry
* unauthorized dashboard access
* replayed heartbeat
* oversized/malformed heartbeat
* SQL injection
* XSS
* session theft
* OAuth misuse
* exposed secrets
* accidental public database exposure
* notification credential leakage
* malicious device-controlled strings
* denial-of-service attempts
* compromised edge device
* compromised central VM

V1 does not claim protection against a fully compromised root account on either the central server or an edge device.

---

# 4. Important Security Limitation

A valid device credential proves:

```text
A request possesses the enrolled device credential.
```

It does NOT cryptographically prove:

```text
the physical machine itself is healthy or uncompromised.
```

If an attacker obtains a device credential, they may potentially submit fabricated telemetry for that device until the credential is revoked.

Therefore:

```text
authenticated telemetry != hardware attestation
```

This limitation must be understood operationally.

---

# 5. Device Identity

Every monitored device receives an immutable:

```text
device_uuid
```

generated by the server.

Example:

```text
8cf5c647-70a0-4559-a4da-1a39dd66c119
```

The UUID must not be derived from:

* hostname
* IP address
* MAC address
* GPU UUID
* Linux machine-id

Human-readable device names are separate metadata.

Example:

```text
device_uuid:
8cf5c647-70a0-4559-a4da-1a39dd66c119

device_name:
Warehouse-GPU-01
```

Renaming or moving a device between projects does not change its UUID.

---

# 6. Per-Device Credentials

Each device receives its own credential.

Never share one global agent token across all devices.

Conceptual format:

```text
sb1.<credential_id>.<secret>
```

The secret should contain at least:

```text
256 bits
```

of cryptographically secure randomness.

The credential ID is an identifier.

The secret is confidential.

---

# 7. Credential Storage

The agent must retain the credential because it needs it for authentication.

Preferred location:

```text
/etc/skybeat-agent/agent.env
```

or a dedicated protected credential file.

Recommended ownership:

```text
root:root
```

Recommended mode:

```text
0600
```

The credential must never be committed to Git.

---

# 8. Server Credential Storage

The central server should not store the raw device secret.

Store:

```text
credential_id

device_id

token_digest

created_at

expires_at

revoked_at

last_used_at
```

The token digest may use:

```text
SHA-256
```

over the canonical complete high-entropy token.

This is appropriate because the device token contains cryptographically random high-entropy material rather than a human password.

Use constant-time comparison where application-side comparison is required.

---

# 9. Device Authentication

Agents authenticate using:

```http
Authorization: Bearer <device-token>
```

Never authenticate agents using:

* hostname
* IP
* project name
* device name
* GPU UUID

The authenticated credential must belong to the same:

```text
device_uuid
```

contained in the heartbeat.

Mismatch:

```text
credential for Device A

heartbeat claims Device B
```

must be rejected.

---

# 10. Credential Validation

For every heartbeat verify:

* token format
* credential exists
* credential belongs to device
* credential is not revoked
* credential is not expired
* device exists
* device is enabled for ingestion

Do not allow a stale positive authentication cache to continue authorizing a credential after revocation.

For the initial fleet size, direct MySQL-backed validation is acceptable.

---

# 11. Credential Rotation

Rotation procedure:

```text
Create new credential
        ↓
Install on device
        ↓
Restart agent
        ↓
Confirm heartbeat with new credential
        ↓
Revoke old credential
```

A temporary overlap is allowed.

Maximum recommended overlap:

```text
24 hours
```

Prefer at most:

```text
2 active credentials/device
```

during rotation.

Never revoke the old credential before confirming that the new credential works unless emergency revocation is required.

---

# 12. Emergency Revocation

An operator must be able to revoke a compromised device credential.

After revocation commits:

```text
future heartbeat authentication using that credential fails
```

Already accepted historical telemetry remains historical evidence.

Revocation does not delete previous heartbeats.

---

# 13. Device Disable

Administrators may disable a device server-side.

Disabling should prevent the device from affecting active monitoring according to the rules defined in `ALERTING.md`.

It must not:

* manufacture a fake outage
* manufacture a recovery
* delete historical telemetry

The administrative action should be audited.

---

# 14. Enrollment

V1 does NOT require public self-enrollment.

Device enrollment is an administrative operation.

For the initial deployment, it may be performed using:

```text
local management CLI
```

running on the central VM.

The operator supplies:

* project
* device name
* GPU monitoring policy
* expected GPU count/UUIDs where applicable

The server generates:

* device UUID
* device credential

The complete credential should be displayed only during deliberate enrollment/rotation output.

---

# 15. Administrative API Scope

A public device-management API is not required for V1.

This reduces attack surface.

Initial administrative actions may use:

* local CLI
* controlled database-backed management service
* migration/admin tooling

Do not expose unnecessary public endpoints simply for convenience.

---

# 16. Dashboard Authentication

The dashboard uses:

```text
Google OpenID Connect / OAuth 2.0
```

using the authorization-code flow.

Use a maintained OIDC library.

Do not manually implement JWT cryptography.

Request only required scopes:

```text
openid

email
```

No Google offline access is required.

No refresh token is required.

---

# 17. OAuth Security

The login flow must use:

```text
state

nonce

PKCE S256
```

where supported by the chosen maintained library and flow.

Validate:

* ID token signature
* issuer
* audience
* expiration
* nonce
* verified email

Do not treat a decoded JWT as authenticated merely because its payload can be read.

---

# 18. Explicit Dashboard Authorization

Successful Google authentication alone is NOT enough.

After authentication, authorize the user using server-controlled configuration.

Supported V1 authorization methods:

```text
explicit email allowlist

and/or

approved Google Workspace domain
```

Example:

```text
SKYBEAT_ALLOWED_EMAILS=
admin@example.com,ops@example.com
```

Optional:

```text
SKYBEAT_ALLOWED_DOMAINS=
example.com
```

Empty authorization configuration means:

```text
deny access
```

not:

```text
allow everyone
```

---

# 19. Domain Authorization

If Google Workspace domain authorization is used, validate Google's verified hosted-domain claim where supported.

Do NOT authorize based only on:

```text
email ends with "@example.com"
```

when domain-level authorization depends on Google Workspace identity.

Do not rely on the OAuth request's domain hint as proof.

Explicit email allowlisting remains the simplest and safest initial V1 configuration.

---

# 20. Dashboard User Identity

Persist the stable Google:

```text
sub
```

identifier.

Optionally store:

```text
verified email

hosted domain

last login

created_at
```

Email is useful for display/audit.

Google `sub` is the stable external identity.

---

# 21. Application Sessions

After successful Google authentication, issue an application-owned opaque session.

Do not use the Google access token as the long-lived SkyBeat session.

Generate a strong random session token.

Store only its digest in MySQL.

Cookie:

```text
__Host-skybeat_session
```

with:

```text
Secure

HttpOnly

SameSite=Lax

Path=/
```

and no `Domain` attribute.

---

# 22. Session Lifetime

Recommended V1 defaults:

```text
absolute lifetime:
8 hours

idle lifetime:
30 minutes
```

These may be tuned operationally.

Server-side expiry is authoritative.

Logout revokes the server-side session and clears the browser cookie.

---

# 23. Google Token Handling

Google tokens should be retained only as long as necessary to validate login.

Do not store Google access/ID tokens in:

```text
localStorage

sessionStorage

frontend JavaScript variables longer than necessary

application logs
```

V1 does not need persistent Google refresh tokens.

---

# 24. OAuth Temporary State

OAuth transactions require temporary server-side state for:

* state
* nonce
* PKCE verifier
* creation/expiry
* browser binding where implemented

Store these records with a short lifetime.

Recommended:

```text
10 minutes
```

Consume them once.

Expired/reused OAuth transactions must fail.

The exact storage implementation should remain simple and compatible with the selected OIDC library.

---

# 25. Dashboard Authorization on Requests

Every protected dashboard/API request must verify:

```text
valid application session

session not expired

session not revoked

user still authorized
```

Read-only JSON endpoints require the same authorization as HTML pages.

Do not assume:

```text
"the endpoint only reads data"
```

means authentication is unnecessary.

---

# 26. CSRF

The initial dashboard is primarily read-only.

Logout should use:

```text
POST
```

rather than GET.

Any browser endpoint that changes server state must use appropriate CSRF protection.

Do not create state-changing GET routes.

---

# 27. XSS Protection

Treat these values as untrusted:

* project name
* device name
* hostname
* IP metadata
* GPU name
* agent version
* telemetry strings

Use:

* template autoescaping
* safe DOM text insertion
* no direct `innerHTML` for untrusted values

Avoid inline JavaScript where practical.

---

# 28. Browser Security Headers

Recommended production headers include:

```text
Content-Security-Policy

X-Content-Type-Options: nosniff

Referrer-Policy: no-referrer

frame-ancestors 'none'
```

Authenticated responses should generally use:

```text
Cache-Control: no-store
```

HSTS may be enabled after HTTPS deployment has been verified.

---

# 29. CORS

The dashboard and API should operate from the same origin where practical.

Therefore V1 should not require permissive CORS.

Do NOT configure:

```text
Access-Control-Allow-Origin: *
```

for authenticated dashboard APIs.

---

# 30. HTTPS

All production agent/server and browser/server communication uses:

```text
HTTPS
```

Agents must validate:

* certificate chain
* hostname
* certificate validity

Never automatically fall back to HTTP.

Never use:

```text
verify=False
```

as a recovery mechanism.

---

# 31. Reverse Proxy

Use:

```text
Caddy
```

or the reverse proxy selected in `DEPLOYMENT.md`.

Responsibilities:

* public TLS termination
* HTTP → HTTPS redirect
* hostname restriction
* request limits
* forwarding to FastAPI

Only the reverse proxy should expose the public application ports.

---

# 32. Public Ports

Recommended external exposure:

```text
80/tcp
443/tcp
```

Port 80 may exist only for redirect/certificate handling.

Do NOT publicly expose:

```text
3306 MySQL

8000 FastAPI

worker ports

Docker internal service ports
```

SSH exposure is an infrastructure/operator decision and should be restricted separately.

---

# 33. MySQL Network Isolation

MySQL 8.x must remain private.

Preferred deployment:

```text
Caddy
   ↓
FastAPI
   ↓
private Docker network
   ↓
MySQL
```

MySQL must not bind publicly unless there is an explicitly reviewed infrastructure requirement.

Production firewall/security-group rules should independently prevent public MySQL access.

---

# 34. Proxy Trust

FastAPI should trust forwarded client information only from the known reverse proxy.

Do not trust arbitrary incoming:

```text
X-Forwarded-For

X-Forwarded-Proto

Forwarded
```

headers from Internet clients.

The proxy should overwrite/sanitize forwarding headers.

---

# 35. Heartbeat Body Limit

Maximum heartbeat request body:

```text
128 KiB
```

Enforce this at:

```text
reverse proxy

and

application
```

Do not rely only on `Content-Length`.

Reject oversized streamed/chunked bodies as well.

---

# 36. Telemetry Limits

Heartbeat validation must bound:

```text
GPUs <= 64

filesystems <= 64

IP addresses <= 16

string lengths

numeric ranges
```

Reject:

* unsupported schema versions
* malformed JSON
* non-finite numbers
* invalid UUIDs
* excessive nesting
* unsupported content types

Exact contracts belong in `API_SPEC.md`.

---

# 37. Never Execute Telemetry

No telemetry value may become:

* shell command
* executable path
* SQL fragment
* filesystem path for arbitrary access
* remote URL fetch target

Telemetry is data only.

---

# 38. SQL Injection Protection

Use:

```text
SQLAlchemy
```

with parameterized statements.

Never construct SQL using string interpolation from:

* heartbeat data
* project names
* device names
* dashboard parameters

Raw SQL, when required for locking or migrations, must still use bound parameters.

---

# 39. Rate Limiting

Rate limiting is defense-in-depth, not the primary security mechanism.

For the initial ≤100-device deployment, keep V1 limits understandable.

Recommended starting limits:

```text
Authenticated heartbeat:
6 requests/minute/device
burst 6

Dashboard:
120 requests/minute/session

OAuth:
reasonable source-IP limit
```

Normal heartbeat traffic is approximately:

```text
2 requests/minute/device
```

so the device limit allows retries and jitter.

---

# 40. Anonymous Heartbeat Protection

Before credential validation, apply a coarse source-IP/admission limit.

It must accommodate multiple monitored devices behind the same NAT.

Do not configure a tiny per-IP limit that blocks an entire site sharing one public address.

Exact proxy/application values should be measured during deployment.

---

# 41. Rate-Limit Implementation

Do not make a complex distributed rate-limiting subsystem a blocker for the first end-to-end V1 milestone.

Initial protection may combine:

```text
reverse-proxy request limits

API concurrency limits

authenticated per-device application limits
```

For the single-VM deployment, application-side limiting is acceptable if its restart behavior and limitations are understood.

If shared persistent rate-limit state becomes necessary, MySQL-backed counters can be added.

Redis is not required for V1.

---

# 42. API Concurrency

Bound simultaneous API work.

Initial target:

```text
approximately 100 in-flight requests/process
```

Actual configuration must be tested against:

* VM CPU
* VM RAM
* MySQL pool size
* heartbeat load

Do not allow unlimited request/task creation.

---

# 43. Request Deadlines

Network and database work must be bounded.

Conceptual targets:

```text
heartbeat API request:
<=10 seconds total

normal handler/database work:
substantially less
```

A slow dependency must not consume resources indefinitely.

---

# 44. Database Timeouts

Configure bounded:

* connection acquisition
* statement execution where supported
* lock waits

A blocked transaction must eventually fail rather than consume a worker indefinitely.

Lock timeout behavior must be tested with MySQL 8.x/InnoDB.

---

# 45. Database Failure

If MySQL is unavailable:

```text
heartbeat acceptance fails

state evaluation pauses

notification persistence pauses

readiness becomes unhealthy
```

The application must NOT:

* bypass authentication
* accept telemetry only in memory
* manufacture incidents in memory
* pretend the system is healthy

Return an appropriate temporary failure such as:

```text
503 Service Unavailable
```

where applicable.

---

# 46. Database Users

Use separate MySQL credentials where practical for:

```text
application runtime

migrations

backup/restore

operator administration
```

The normal application user must not have:

* global administrative privileges
* user-management privileges
* unrestricted DDL
* FILE privilege
* SUPER-style administrative privileges

Grant only required database/table operations.

---

# 47. Application Runtime User

FastAPI and worker containers/processes should run as non-root.

Where compatible:

* drop unnecessary Linux capabilities
* prevent privilege escalation
* use read-only application filesystem
* provide bounded writable temporary locations

Do not mount:

```text
/var/run/docker.sock
```

into application containers.

---

# 48. Agent Runtime User

Preferred Linux agent account:

```text
skybeat
```

The agent should run without root privileges where practical.

It needs only:

* system telemetry access
* NVIDIA telemetry access
* outbound HTTPS
* access to its configuration

It does NOT need:

* sudo
* Docker socket
* SSH private keys
* arbitrary filesystem write access
* system configuration permissions

---

# 49. Agent Configuration Security

Recommended:

```text
/etc/skybeat-agent/agent.env
```

with:

```text
owner:
root

mode:
0600
```

The systemd service manager may load the file and pass required configuration to the unprivileged agent.

If environment exposure is unacceptable for a deployment, a protected credential file may be used later.

---

# 50. NVIDIA Subprocess Security

The GPU collector uses a locally configured trusted absolute path:

```text
/usr/bin/nvidia-smi
```

with:

* fixed approved query arguments
* argument-array execution
* `shell=False`
* bounded output
* timeout
* controlled environment

No heartbeat/server value may become an `nvidia-smi` argument.

The collector must never execute mutation operations.

---

# 51. Secret Management

Secrets include:

* MySQL password
* device tokens
* Google OAuth client secret
* OAuth state-encryption key if used
* SMTP credentials
* SMS API credentials
* backup encryption keys

Secrets must not be committed to Git.

Commit only:

```text
.env.example
```

containing variable names/placeholders.

---

# 52. Deployment Secret Injection

For V1, root-restricted environment/secret files are acceptable.

Do not place secrets in:

* Dockerfile
* image layers
* repository files
* command-line arguments
* screenshots
* documentation examples using real credentials
* support tickets
* normal logs

A dedicated secret manager can be introduced later without redesigning the application.

---

# 53. Logging

Structured logs should include safe operational identifiers such as:

```text
timestamp

severity

component

request_id

device_id

incident_id

delivery_id

safe error category
```

Do not routinely log complete heartbeat payloads.

---

# 54. Log Redaction

Never log:

```text
Authorization header

device token

session cookie

Google authorization code

Google token

OAuth state/nonce values

MySQL password

connection string with password

SMTP password

SMS API secret

complete secret files
```

Exception handlers must use safe/redacted output.

---

# 55. Notification Privacy

By default, notifications should contain only operationally useful information.

Recommended:

```text
project name

device name

event type

timestamp

incident ID

brief reason
```

Avoid including detailed telemetry unless required.

Do not include credentials or secrets.

---

# 56. Sensitive Monitoring Data

Operational monitoring data may include:

* hostnames
* IP addresses
* GPU hardware identifiers
* device UUIDs
* infrastructure/project names

Treat this information as internal operational data.

Only authorized dashboard users and operators should access it.

---

# 57. Retention

Initial proposed retention:

```text
raw telemetry:
7 days

incidents/events:
90 days minimum

notification delivery history:
90 days

security/audit history:
90 days minimum

expired OAuth transactions:
delete promptly

expired sessions:
delete promptly

backups:
30 days
```

These values are configurable and may be adjusted after observing storage requirements.

Active incidents/nonterminal deliveries must not be deleted by routine retention cleanup.

---

# 58. Backups

MySQL backups must be:

* automated
* access-controlled
* stored outside the running database volume
* periodically restore-tested

Off-host backups are strongly preferred.

If backup encryption is available in the deployment environment, use it.

Backups contain sensitive operational metadata and credential digests.

---

# 59. Audit Log

Record important administrative/security events such as:

```text
device enrollment

device disable/enable

credential creation

credential revocation

credential rotation

project reassignment

GPU policy change

authorized-user changes

operator login/admin actions where applicable
```

Audit records should include:

```text
actor

action

target

timestamp

safe metadata
```

Do not place raw credentials in audit data.

---

# 60. Google Authorization Changes

Removing a user from the application allowlist should prevent new authorized sessions.

Existing sessions for that user should be revocable.

For V1, authorization may be re-evaluated against current server configuration on each protected request or sessions may be explicitly revoked during controlled configuration changes.

The chosen implementation must be documented.

---

# 61. Security Failure Behavior

Security uncertainty should generally fail closed.

Examples:

```text
unknown device credential
    → reject

revoked credential
    → reject

device/credential mismatch
    → reject

invalid Google token
    → reject

user not allowlisted
    → reject

expired session
    → reject

database unavailable during authentication
    → temporary failure, not allow
```

Do not silently downgrade security controls to preserve availability.

---

# 62. Central VM Compromise

If the monitoring VM is suspected compromised:

1. restrict/isolate network access
2. preserve required evidence
3. rotate infrastructure/provider secrets
4. rebuild from a trusted image where appropriate
5. restore MySQL from a trusted backup
6. invalidate dashboard sessions
7. review device credentials
8. verify agent communication before reopening access

Do not assume a compromised VM can be safely repaired in place.

---

# 63. Device Credential Compromise

If one device token is suspected compromised:

1. revoke that credential
2. inspect recent heartbeat/audit history
3. issue a replacement credential
4. install it securely on the intended device
5. verify heartbeat authentication
6. retain historical evidence

Compromise of one device token must not grant access to another device.

---

# 64. Database Restore Security

Restoring an older MySQL backup may restore:

* revoked credentials
* expired sessions
* old authorization state

After security-sensitive restore:

* invalidate application sessions
* reconcile credential revocations
* verify authorized users
* verify provider credentials/configuration
* inspect audit continuity

Do not immediately expose a restored system publicly without this review.

---

# 71. V1 Security Priorities

Because V1 must deploy quickly, implement security in this order:

```text
1. HTTPS

2. Per-device credentials

3. Server-side token hashing

4. Device/credential binding

5. Strict heartbeat validation

6. MySQL network isolation

7. Secrets outside Git

8. Non-root application/agent execution

9. Google authentication

10. Explicit dashboard allowlist

11. Secure application sessions

12. Request/body limits

13. Basic rate limiting

14. Log redaction

15. Credential rotation/revocation

16. Security failure testing

17. Additional hardening
```

Do not delay the core monitoring path by building an unnecessarily complex security framework first.

However, never deploy publicly without:

```text
HTTPS

per-device authentication

dashboard authorization

private MySQL

protected secrets
```

# 74. Security Success Criteria

V1 security succeeds when:

* each device has an independent identity and credential
* compromise of one device token does not authorize another device
* device tokens are not stored raw server-side
* revoked credentials stop working
* heartbeats are accepted only over authenticated HTTPS
* telemetry is strictly validated and never executed
* dashboard requires Google authentication
* dashboard access requires explicit authorization
* sessions are protected server-side
* MySQL is not publicly reachable
* application services use least privilege
* secrets are absent from Git/logs
* notification-provider credentials remain protected
* security failures fail closed
* operational actions remain auditable
* no monitoring feature provides remote device control

The V1 security model is therefore:

```text
IDENTIFY
   ↓
AUTHENTICATE
   ↓
AUTHORIZE
   ↓
VALIDATE
   ↓
OBSERVE
   ↓
RECORD
```

Never:

```text
OBSERVE
   ↓
EXECUTE ON DEVICE
```

Remote operations require a separately designed future security model and are outside SkyBeat V1.
